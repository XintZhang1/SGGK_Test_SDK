# SGGK Source Attack

## Purpose

Convert source-code suspicions into machine-readable attack DSL for the SGGK test harness. Prefer DSL that `sggk_case_runner` can execute directly; `compile_attack_dsl.py` is a compatibility/debugging path. When the source points to an unsupported API, emit a clear harness-extension request plus a proposed DSL extension.

## Workflow

1. Inspect source with fast text search first: magic constants, tolerance comparisons, special-case branches, disabled checks, TODO/FIXME, `Precision::`, `1e-`, `EPS`, `Tol`, `toler`, `near`, `parallel`, `degenerate`, `seam`, `periodic`, `singular`, `merge`, `split`. For broad source roots, run `python .\test_harness\tools\scan_source_risks.py <source-root> --out .\artifacts\source_risk_scan` first, then read `source_risk_report.md`, `source_risk_report.json`, and `attack_seed_drafts.json`. For small-model inference or distillation, run `build_source_attack_tasks.py <source_risk_report.json-or-dir> --out <task-dir>` to produce `source_attack_tasks.jsonl` with wider source excerpts and review-required seed DSL. Treat scan/task output as a prioritization aid and still inspect the cited source before emitting final DSL.
2. Identify the fragile predicate: the condition that could change behavior near a boundary, silently skip validation, produce invalid topology, or lose geometry/topology provenance.
3. Map the predicate to a harness action:
   - Use the attack DSL for subtraction/intersection/union attacks. The runner can build direct primitives, rectangular extrusions, line sweeps, BSpline support-face sweeps, line-profile revolves, closed-profile revolves, and a pre-boolean cylinder-minus-wedge body before the outer boolean.
   - Use `generate_boolean_matrix.py` for broad boolean baseline slices or for expanding a source-directed hypothesis into an OCC-style matrix lane.
   - Use `generate_corpus_recut_matrix.py` when existing `.sgt` samples, imported outputs, reduced failures, or artifact bodies should be re-attacked as `loaded_sgt` boolean targets. Pass the runner so tool placement can use exact coordinate-plane distance extrema instead of conservative SDK bboxes; require exact probing for bug-filing lanes.
   - Use `check_sgt` for saved failing or suspicious `.sgt` models.
   - Use `step_import` or `iges_import` for exchange corpus files.
   - Use `step_roundtrip` or `iges_roundtrip` for `.sgt` sources when the risk is export/import drift, BSpline conversion, or ret-success-but-geometry-changed behavior.
   - Add `expectations` when the source implies a measurable true-result predicate, such as non-empty result, sampled boolean volume relation, critical point/body relation, point/face relation, expected body/body clash relation, minimum clearance or distance, exact coordinate extrema, bounded area growth, monotonic volume, or expected total length/area/volume range.
   - If the API is not supported yet, output `needs_harness_extension`.
4. For model-generated DSL, run `compile_attack_dsl.py --check --report <report.json>` before compiling or running it. Keep the report outside compiled recipe directories so later `validate_recipe.py <compiled-dir>` scans only recipe JSON files.
5. For local corpus batches, run `discover_corpus.py` first, audit the frozen `dataset_index.json` with `audit_corpus_dataset.py`, then pass the index or path list to `run_corpus.py --dataset-list`. For STEP/IGES corpora with likely complex curves/surfaces, run `profile_cad_features.py --dataset-list <dataset_index.json>` and prefer `complex_dataset_index.json` as a focused exchange/roundtrip subset before broadening to the whole corpus; use `complex_paths.txt` only for quick compatibility flows. For SGT exchange checks, repeat `--sgt-api check_sgt --sgt-api step_roundtrip --sgt-api iges_roundtrip` as needed. For SGT recut attacks, pass the same dataset index to `generate_corpus_recut_matrix.py`, or discover previous import artifacts with `--include-artifacts`.
6. For generated flat recipe batches, run `run_recipes.py` so each case is process-isolated and command failures are captured.
7. For full local campaigns, use `run_campaign.py` to combine corpus discovery/run, dataset audit, corpus recut lanes, generated matrix lanes, DSL lanes, aggregate triage, replay, previews, geometry audit, oracle coverage, failure bundles, bug registry collection, GUI-ready debug handoff packs, bug-record draft export, optional promoted bug-record candidate replay, and artifact verification. Use `--promote-bug-records --replay-promoted-bug-records` when direct campaign drafts should immediately become portable review candidates plus candidate-root materialization/replay/regression evidence. Let `--corpus-recut-use auto` prefer corpus output artifacts; choose `original` or `both` only when raw SGT inputs must also be re-attacked. Use `--discover-include-artifacts` when historical harness outputs and failure bundles should become part of the corpus. For large runs, prefer `plan_large_campaign.py` first: it freezes corpus discovery, applies `smoke` / `standard` / `stress` profiles, emits `commands/preflight.ps1`, shard scripts, and `commands/run_all_with_preflight.ps1`, and runs source scan/task packaging in shard 0 by default. Use planner/preflight `--profile-cad-features` for STEP/IGES-heavy runs, `--require-cad-feature-profile` when a missing/empty complex subset should block the batch, and planner `--use-cad-feature-subset` when shards should directly attack the plan-time `cad_feature_profile/complex_dataset_index.json` instead of the full frozen dataset. Direct `run_campaign.py --shard-count N --shard-index I` is still valid for hand-written split jobs; treat `empty_shard=true` lane summaries as normal when a small lane has no work in a shard. Before a long run, execute `preflight_campaign.py` or the planner's generated preflight and report ok/error/warning counts, DSL recipe count, bug-record count, dataset audit status, CAD feature profile/subset audit status when enabled, and dataset evidence. Report `dataset_audit/dataset_audit.md`, `oracle_coverage/oracle_coverage.md`, and `campaign_verification/campaign_verification.md`; manually rerun `verify_campaign_artifacts.py --campaign <root>` only when reviewing an existing or merged root.
8. After split campaigns finish, run the planner's `commands/collect_shards.ps1` or use `collect_campaign_shards.py` to merge shard roots into one report, one reduction index with fingerprint groups when shard reductions exist, optional `reduction_replay/` for canonical reduced recipes, optional `reduction_bug_record_drafts/` from reduced replay triage, one bug registry, one GUI debug-handoff directory, one bug-record draft file with matching handoff evidence when available, optional promoted portable bug-record candidates, optional promoted-candidate replay/regression status, and optional materialized bug-record registry.
9. For post-run analysis, use `triage_artifacts.py` on runner, recipe-lane, or corpus artifact roots to produce `triage_summary.json`, `triage_report.md`, and `regression_seeds.json`.
10. Render preview screenshots with `render_case_preview.py`, then run `audit_case_geometry.py --exact-bbox-runner <runner>` or `run_recipes.py --geometry-audit-out` for tolerance families. Inspect contact sheets and use signed-clearance/geometry-hash evidence to catch duplicate cases and wrong-side tolerance sweeps.
11. Replay representative regression seeds with `replay_regression_seeds.py` before filing bugs or starting reduction. Treat `stable_failure` as reducer-ready, `flaky` as needing more retries or isolation, `not_reproduced` as stale/synthetic/environment-dependent, and `unavailable` as missing required source artifacts.
12. When a recipe lane crashes after status/topo-check output but before `report/validation.json`, run `probe_topotrack_crashes.py --runner <runner> --summary <recipe_summary.json> --out <probe-dir>` before filing a modeling bug. Treat `topotrack_only_modeling_ok` as diagnostic evidence only; continue bug filing only when disabling topo tracking still produces a modeling, validation, or crash failure.
13. Reduce stable flat-recipe failures with `reduce_failure_recipe.py` when the representative case is too large, or use campaign `--reduce-stable-failures` for bounded opt-in reduction after aggregate replay. Preserve the baseline failure predicate and keep legal dimensions above the `1e-2` modeling tolerance unless source-specific evidence says otherwise. Report `reductions/reduction_index.md` from the campaign root or merged shard root when reduction was enabled; report `reduction_replay/` and `semantic_check.md` when canonical reduced recipes were replayed during shard collection. Do not require reduction and replay triage fingerprints to match; use semantic check status instead. Use `--export-reduction-bug-record-drafts` only with `--replay-reductions` when those replayed smaller repros should become reviewable draft bug records.
14. Export stable failures with `export_failure_bundles.py --zip` when a handoff-ready bug report needs recipes, input files, key reports, debug-geometry SGTs, previews, replay status, a `reproduce.ps1` script, `localization_summary.json`, and topology localization in one directory.
15. Collect campaign or bundle results with `collect_bug_registry.py` when failures need a persistent index across runs. Report replay status, primary contact topology, bug report paths, and replay recipes.
16. Build GUI-oriented debug packs with `build_debug_handoff.py --registry <bug_registry>` or use the campaign's default `debug_handoff/` output. For known-bug replay lanes, pass both `--registry <known_bug_records>` and `--triage <known_bug_replay_triage>` so packs keep durable bug fingerprints while using the latest replay SGTs and focus topology. When `sggk_topology_extract.exe` is available, expect `focus/*.sgt` files for the primary target/tool contact topology in addition to debug and input SGTs; every pack should also have `visual_index.json` / `visual_index.md` listing all GUI-openable SGTs and `focus_index.json` / `focus_index.md` with extraction status. Report the pack path, visual index, focus index, and copied debug/focus/input SGT counts when a failure needs manual GUI inspection.
17. Convert stable triage groups or failure bundles into editable bug-record drafts with `export_bug_record_drafts.py` before checking them in; pass `--debug-handoff <debug_handoff_index_or_dir>` whenever GUI packs exist so drafts preserve `visual_index.md`, `focus_index.md`, `sgt_paths.txt`, and copied SGT counts for the same fingerprint. Direct campaigns and merged shard collection do this automatically. For merged reduced replay outputs, prefer the collector's `reduction_bug_record_drafts/drafts.json` as a review aid because it points at canonical reduced recipes and carries `reduction_replay_evidence`; use `--materialize-reduction-bug-records` when the reduced drafts should also become a temporary registry plus regression status report. Preserve original/replay recipes, debug-geometry SGTs, input SGTs, GUI handoff evidence, oracle details, topo-track diagnostics, and source-task provenance such as `source_task_id`, `source_ref`, and `source_risk_id`.
18. For confirmed known bugs that should survive as version-regression assets, review the draft or write bug-record JSON, promote campaign-local drafts with `promote_bug_records.py` when replay assets still point at `artifacts/`, run `audit_bug_record_portability.py`, and materialize with `record_bug_cases.py`. In direct campaigns, prefer `run_campaign.py --promote-bug-records --replay-promoted-bug-records`; in merged campaigns, prefer `collect_campaign_shards.py --promote-bug-records --replay-promoted-bug-records --runner <runner>` when the promoted candidate should also be materialized, replayed, and classified from its candidate root before review. Use `validation_failures` for generic validation oracles, `roundtrip_failures` for STEP/IGES source/result comparison oracles, and `topo_track_policy: diagnostic_when_modeling_fails` when modeling/result validation is the bug and topo tracking is only localization context. Prefer `replay.recipe` or `replay.recipe_path` for reduced flat repros; use `replay.dsl_path` / inline `replay.dsl` plus `case_id` or `dsl_case_id` + `dsl_variant` when the durable repro should preserve formal DSL modeling history. If a record came from corpus artifacts, copy the minimal durable SGT inputs under `test_harness/fixtures/bug_records/<id>/` and point replay recipes at that fixture instead of temporary campaign paths; `promote_bug_records.py` automates that copy/rewrite for draft records and strips transient GUI launcher paths while keeping a handoff-summary observation.
19. Re-run persistent registries with `run_recipes.py --recipe-list <registry_replay_recipes.txt>`, then run `check_bug_registry_regression.py` against the fresh `recipe_summary.json` when checking open bug regressions. Report `still_failing`, `fixed_or_not_reproduced`, `changed_failure`, and `unavailable` separately.
20. Emit JSON only after reading the relevant references:
   - For preferred model-generated attack format, read `references/attack-dsl.md`.
   - For compiled recipe fields and supported APIs, read `references/recipe-schema.md`.
   - For geometry/topology attack patterns, read `references/attack-heuristics.md`.
   - For final answer structure, read `references/output-contract.md`.
21. Include source references, the hypothesis, screenshot/preview commands, registry/debug-handoff/bundle paths, and minimization hints with every proposed case.

## Guardrails

- Do not ask the small model to call SDK APIs directly; generate attack DSL for the C++ runner.
- Name important chain steps with stable `id` values so topology-tracking artifacts, compiled flat recipes, and triage contact candidates can refer back to modeling operations.
- Name reused critical probes under DSL `key_points` and reference them with `point_ref`; the compiler/native DSL runner resolves them to flat `point` coordinates while preserving the probe name in validation records.
- For failed or suspicious runs, localize through `topo_track_summary.json`, then `topo_track.json` ancestor `input_ref`, then `input_topology_index.json` locators. If topo tracking is skipped, use triage `input_contact_candidates`.
- Prefer legal but adversarial geometry over impossible input unless the source branch explicitly handles invalid input.
- Preserve numeric values exactly from source when relevant, then create nearby variants around the threshold.
- Treat `scan_source_risks.py` DSL seeds as review-required drafts. Keep their source references and risk categories, but edit geometry, expectations, and exact plane-extreme values after reading the source branch.
- Treat `build_source_attack_tasks.py` output as model input, not as ground-truth labels. It is allowed to include seed DSL, but generated final DSL must still be compiled, rendered, audited, and reviewed.
- Use SGGK scale constants unless source code proves otherwise: topology/modeling tolerance `1e-2`, pure geometry tolerance `1e-5`, and maximum intended modeling coordinate/size `5e5`.
- Always include a deterministic seed or exact parameters.
- Treat API success with invalid topology as a failure condition.
- Treat API success with failed `report/validation.json`, clash-relation violations, point/body or point/face relation violations, distance-oracle violations, or impossible result properties as a failure condition.
- Treat SDK bbox relation mismatches as conservative diagnostics only. Use `expectations.plane_extreme_checks` when the exact min/max coordinate is the intended hard oracle; this uses coordinate-plane distance probes rather than trusting SDK bbox values. Use `compare_expected=false` or `probe_exact_bbox.py` when the task is measuring an exact bbox rather than asserting a known coordinate.
- For corpus recut generation and tolerance-family audits, pass `--runner` / `--exact-bbox-runner` so exact extrema come from coordinate-plane distance probes. Use fallback named-point/bbox estimates only for exploration, not for filing extent-sensitive bugs.
- Before treating a bug record as checked-in regression data, run `audit_bug_record_portability.py`; absolute local paths and `artifacts/` dependencies belong in drafts or campaign evidence, not long-lived records.
- Treat API success with failed `report/roundtrip_comparison.json` as a failure condition for STEP/IGES roundtrip lanes; report metric deltas and tolerances.
- Use `sample_input_properties: true` only for stable solid boolean cases where target/tool volume is part of the oracle; leave it off for broad fuzz lanes unless probing property robustness.
- Do not trust generated sweep/support-sweep/revolve/tolerance variants until preview screenshots and geometry audit show the intended bbox/parameter differences or the contact-sheet signatures intentionally match.
- For corpus recut lanes, report both the original corpus path and the generated target/tool contact candidates; SGT edge/sheet bodies may be useful degeneracy probes even when they are not solid-volume tests.
